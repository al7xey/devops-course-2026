# Подготовка к КР

## Когда rebase, а когда merge?

Rebase использую для своей локальной ветки, которую ещё никто не видел: перед PR подтягиваю свежий main через `git rebase main` и чищу коммиты через `rebase -i`. История получается линейной и её проще читать.

Merge использую, когда вливаю ветку в общую (main, develop) или когда ветка уже запушена и с ней работают другие. Merge не переписывает коммиты, плюс по merge-коммиту видно, когда и что было влито.

## Что будет, если сделать rebase публичной ветки?

У всех коммитов ветки поменяются хеши. У коллег останутся старые коммиты, и при следующем pull Git увидит две разные истории: появятся дубли коммитов, конфликты, а чтобы залить свою версию, придётся делать `push --force` и можно затереть чужую работу.

## Зачем нужен multi-remote?

Чтобы один локальный репозиторий был связан с несколькими удалёнными. Примеры:
- зеркало на другой площадке (GitHub + GitLab/Gitverse) как резервная копия или на случай блокировок;
- работа с форком: `origin` - свой форк, `upstream` - оригинальный репозиторий, откуда забираются обновления;
- отдельный remote для деплоя (например, push на сервер или в корпоративный GitLab, где настроен CI).
